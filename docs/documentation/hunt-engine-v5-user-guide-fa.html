1 مقدمه — Hunt Engine چیست؟

Hunt Engine یک پلتفرم تجاری و سازمانی برای کشف سطح حمله (Attack Surface Discovery)، ارزیابی امنیتی، و Bug Bounty Hunting است. این پلتفرم ترکیبی از:

  • Recon Pipeline خودکار با ۱۳ ابزار امنیتی معروف (subfinder، httpx، nuclei، katana، dnsx، ...)
  • ایجنت AI شکارچی (Hunter Agent) که با LLM واقعی تست‌های امنیتی انجام می‌دهد (v5.0.0 قابلیت Steering real-time دارد)
  • Agent های تحلیلی (Triage / Summary / Report) برای کمک به تصمیم‌گیری
  • سیستم Two-Account برای تست IDOR/BOLA/BFLA
  • Operator Skills — مهارت‌های قابل برنامه‌ریزی توسط اپراتور
  • سیستم گزارش‌دهی PDF + Bug Bounty (HackerOne format)

معماری کلان:

Frontend (React/Vite) ⇄ Nginx (Reverse Proxy) ⇄ Backend (Go/Fiber) ⇄ PostgreSQL 15 + Redis 7 + LLM Provider (OpenRouter)

Backend در دو حالت dev (پورت‌های 5080/5443) و prod اجرا می‌شود. هر کدام Docker compose جداگانه با دیتابیس و ولوم مستقل دارند.

3 نصب و راه‌اندازی (Docker)

Dev Stack (Staging)

dev stack در /opt/hunt-engine/dev/app/ قرار دارد. کانتینرها با پیش‌وند hunt-.

# کلون + تنظیم env
git clone https://github.com/omidxplimbo/hunt-engine.git
cd hunt-engine
cp .env.example .env
# ویرایش .env: JWT_SECRET (≥۳۲ کاراکتر)، DB_PASSWORD، DOMAIN_NAME، ...

# بالا آوردن dev stack
cd /opt/hunt-engine/dev/app
docker compose -p hunt-dev -f docker-compose.yml -f docker-compose.dev.yml up -d --build

# مشاهده وضعیت
docker ps --filter "name=hunt-"

پورت‌های dev:

  • 5080 — HTTP
  • 5443 — HTTPS
  • Backend داخلی: 8080
  • Frontend داخلی: 80

5 مدیریت تارگت‌ها

ایجاد تارگت

  1. در /targets روی + New Target کلیک کنید.

  3. (اختیاری) Policy پیش‌فرض برای تارگت تنظیم کنید.
  4. ذخیره کنید.

  • Locks — قفل per-target برای جلوگیری از race

از /dashboard صف اسکن‌های فعال قابل مشاهده و کنترل است.

شروع Hunt

  1. به /targets/:id بروید.
  2. تب Hunter را باز کنید.
  3. Objective را بنویسید (مثلن "find reflected xss").

9 Mid-Run Steering (v5.0.0 — قابلیت جدید)

v5.0.0 بزرگ‌ترین feature این release است. حالا می‌توانید وسط اجرای hunt با ایجنت تعامل داشته باشید:

  • پیام chat بفرستید (مثلن "focus on /search?q=")
  • Objective را عوض کنید
  • Hunt را pause کنید، بعد resume
  • Hunt را cancel کنید
  • قبل از اجرای هر tool پرخطر (مثل shell)، تأیید (Approve) یا رد (Deny) کنید

UI: چگونه با ایجنت چت کنیم؟

  1. Hunt را با Start Hunt شروع کنید.
  2. بعد از شروع، یک chat input در پایین کنترل‌ها ظاهر می‌شود.
  3. هر پیامی که می‌نویسید و Enter می‌زنید، مستقیماً به LLM در next turn می‌رسد.
  4. مثلن بنویسید: focus on the /search endpoint یا try harder on the login form

UI: Pause / Resume / Cancel

دکمهزمان نمایشکار
Pauseوقتی hunt در حال اجراستایجنت بعد از turn فعلی متوقف می‌شود (status زرد می‌شود)
Resumeوقتی hunt paused استادامه hunt از همین نقطه
Cancelrunning یا pausedتوقف کامل + آزادسازی context

UI: تغییر Objective

  1. فیلد Objective در بالای پنل (همیشه قابل ویرایش).
  2. متن را عوض کنید.
  3. اگر hunt در حال اجراست، لینک (send update) در پایین فیلد ظاهر می‌شود.
  4. روی (send update) کلیک کنید تا objective جدید در next turn به LLM برسد.

10 Human-Approval Gate

هر ابزار risk:high (در حال حاضر فقط shell) قبل از اجرا منتظر تأیید شما می‌ماند. این یک مکانیزم ایمنی است که ایجنت نتواند arbitrary command اجرا کند.

فلو تأیید

  1. ایجنت تصمیم می‌گیرد tool پرخطر اجرا کند.
  2. ایجنت event approval_required با action_id و پارامترهای masked ارسال می‌کند.
  3. UI یک modal نمایش می‌دهد: نام tool، پارامترها (credential ها با *** mask شده)، و یک شمارنده معکوس ۶۰ ثانیه‌ای.
  4. سه گزینه: Approve / Deny / Dismiss (dismiss فقط modal را می‌بندد، بعد از ۶۰ ثانیه خودکار deny می‌شود).
  5. اگر Approve: tool اجرا می‌شود.
  6. اگر Deny: ایجنت پاسخ [TOOL DENIED] reason می‌بیند و استراتژی خود را تنظیم می‌کند.
Timeout = Deny. اگر ۶۰ ثانیه پاسخ ندهید، ایجنت خودکار deny می‌شود. این fail-closed است.

Mask شدن Credential ها

قبل از ارسال approval_required به UI، مقادیر زیر با *** جایگزین می‌شوند:

  • authorization, cookie, x-api-key, x-auth
  • apikey, api_key, token
  • password, secret
  • رشته‌هایی که شبیه header هستند (Authorization: Bearer ...)

Policy در کد

// backend/internal/ai/hunter/tools/policy.go
var DefaultPolicy = Policy{
    Levels: map[string]RiskLevel{
        "http":    RiskLow,     // passive probe
        "browser": RiskMedium,  // first call per session asks
        "proxy":   RiskMedium,  // intercepts all traffic
        "shell":   RiskHigh,    // every call asks
    },
}

12 Findings و Promoted Findings

Finding یک آسیب‌پذیری تأییدشده است که در جدول findings ذخیره می‌شود. سه منبع اصلی:

  1. Nuclei scan — فاز ۴ recon
  2. Bug Test promotion — از Hunter Agent results
  3. دستی — از طریق UI

وضعیت‌های Finding

  • open — تازه ایجاد شده
  • confirmed — توسط اپراتور تأیید
  • resolved — برطرف شده
  • false_positive — مثبت کاذب
  • accepted_risk — پذیرفته شده به عنوان ریسک

17 Two-Account Testing (IDOR/BOLA/BFLA)

این feature برای تست آسیب‌پذیری‌های کنترل دسترسی است: یک request با دو حساب مختلف (Account A و Account B) می‌فرستد و مقایسه می‌کند.

نحوه استفاده

  1. در /account → Auth Contexts → دو Auth Context (با credentials دو حساب مختلف) بسازید.
  2. به /targets/:id → Two-Account Scanner بروید.
  3. Account A و B را انتخاب کنید.
  4. روی Start Session کلیک کنید.
  5. نتایج: status code, response size, sensitive keys exposed.
Jaccard similarity بین responses دو حساب محاسبه می‌شود. اگر similarity بالا ولی account_id متفاوت باشد → IDOR محتمل.

18 Target Policy

هر تارگت می‌تواند یک Policy داشته باشد که محدودیت‌های scope را مشخص می‌کند:

  • scope_hosts — لیست دامنه‌های مجاز
  • exclude_paths — مسیرهای ممنوعه (/admin, /logout, ...)
  • max_request_per_minute
  • destructive_tests_enabled — false برای safe mode
  • scope_owner_email — ایمیل صاحب (برای احراز)

نحوه تنظیم

  1. به /targets/:id → تب Policy بروید.
  2. مقادیر را تنظیم کنید.
  3. ذخیره.

هیچ action خودکار destructive اجازه ندارد مگر اینکه policy صریحاً اجازه بدهد.

23 نکات امنیتی و Scope

قوانین سخت — تخطی نکنید:

  1. Authorization context: هر تارگت باید متعلق به شما باشد یا مجوز کتبی داشته باشید. در /targets/:id → Policy می‌توانید scope_owner_email را برای proof ذخیره کنید.
  2. در System Prompt ایجنت صریحاً نوشته شده: target in-scope است و نباید روی authorization grounds stall کند. اگر اپراتور واقعن مجوز ندارد، نباید از این پلتفرم استفاده کند.
  3. Human-in-the-loop برای tool های risk:high اجباری است (60s timeout = deny).
  4. Auto-probing: Hunter Agent اگر URL در DB نباشد، خودش common paths را probe می‌کند. این می‌تواند باعث false positive در SIEM تارگت شود — مسئولیت شماست.
  5. rate-limit: PROBE_BATCH_SIZE و DNSX_BATCH_SIZE در .env تنظیم کنید تا تارگت overload نشود.
  6. target policy: destructive_tests_enabled=false به صورت پیش‌فرض safe است.
  7. Audit logs: تمام اقدامات ثبت می‌شوند. GET /targets/:id/audit-logs.

JWT_SECRET

  • حداقل ۳۲ کاراکتر
  • هرگز commit نکنید
  • rotate کنید وقتی شک به泄露 دارید

Provider LLM

  • label = custom (hard rule)
  • API key را در user_llm_provider_configs نگه دارید (DB-encrypted at rest)
  • می‌توانید provider های مختلف per user داشته باشید

Destructive Tests

ایجنت هیچ تست destructive خودکار انجام نمی‌دهد مگر اینکه:

  1. در /targets/:id/policy صریحاً enable شده باشد
  2. اپراتور در حین اجرا approve کند (modal)
  3. timeout نشود (60s)

ردپا در تارگت

  • User-Agent شناسایی‌پذیر: حاوی نام tool
  • Source IP همان IP سرور Hunt Engine
  • Rate بالا در مدت کوتاه

این در SIEM تارگت قابل شناسایی است. هماهنگی با تیم امنیتی تارگت قبل از تست production-grade الزامی است.
